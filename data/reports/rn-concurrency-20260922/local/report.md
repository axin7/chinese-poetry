# 本地全量诗词服务并发实测

测试时间：北京时间 2026-09-22 02:40:00—02:44:09，分阶段执行。

结论：当前本地实例完成了 **1,232 次不同文本的真实语义检索，全部成功**。
4 并发连续请求实测 12.31 次/秒，16 并发实测 16.52 次/秒；64 个同时到达的请求也全部
成功，但 P95 已达到 4.17 秒，接近模型调用含排队的 5 秒预算。
这组结果支持把本地实例的初始运营区间设为约 4—16 个在途请求、10—12 次/秒的保守限流，
随后依据更长时间的运行数据调整。没有测到失败拐点，不能把 64 并发称为最大承载能力。

**测试机器是本地 Apple M2，不是 rn。不能据此声称 rn 能承载相同流量。**

## 条件与方法

| 项目 | 本次条件 |
|---|---|
| 本地宿主机 | Apple M2，24 GiB 内存 |
| Docker 虚拟机 | 8 个 CPU，11.74 GiB 内存 |
| 接口 | `POST http://127.0.0.1:8000/search` |
| 语料 | 1,717,558 条向量，389,593 部作品，29 个数据集 |
| 模型 | 配置中的 SiliconFlow `BAAI/bge-m3`，1024 维 |
| embedding 并发/超时 | 4 / 5 秒，等待并发槽位也计入超时 |
| 重排 | 当前默认关闭，没有额外调用重排模型 |
| Qdrant | 1.15.5，INT8 量化驻留内存，原始向量存磁盘，HNSW EF=64 |
| 检索参数 | 近似向量查询，top-1，不进行原始向量重评分 |
| 缓存处理 | 全部 1,232 个请求文本不同，未复用历史请求文本 |
| 结果检查 | 每次检查 HTTP 200 且原文、译文非空；另检查 3 部作品全文原译文数组对齐 |

使用组合生成的英文自然语言诗词需求，覆盖思乡、友谊、四季、旅途等主题。
每个请求都经过本地 API → 远程 embedding → 全量 Qdrant 检索 → SQLite 取文链路。
没有把相同文本的缓存命中、向量直传或健康检查吞吐冒充自然语言检索吞吐。
结果只验证结构完整性，没有对这些合成查询逐条进行语义相关性评分。

## 连续请求与突发请求

吞吐按成功数除以实际墙钟时间计算，包含阶段末尾未完成请求的排空时间。
P50、P95 均为成功请求的端到端响应时间，用线性插值计算。

| 阶段 | 请求数/成功数 | 实际耗时 | 成功吞吐 | P50 | P95 | 最大耗时 |
|---|---:|---:|---:|---:|---:|---:|
| 固定 4.5 次/秒，20 秒 | 90/90 | 20.13 秒 | 4.47 次/秒 | 0.195 秒 | 0.455 秒 | 2.016 秒 |
| 持续 4 并发，25 秒发请求 | 311/311 | 25.27 秒 | 12.31 次/秒 | 0.192 秒 | 0.993 秒 | 2.611 秒 |
| 持续 16 并发，25 秒发请求 | 435/435 | 26.34 秒 | 16.52 次/秒 | 0.867 秒 | 1.557 秒 | 2.149 秒 |
| 32 并发，仅一波同时到达 | 32/32 | 1.57 秒 | 20.34 次/秒 | 0.903 秒 | 1.463 秒 | 1.535 秒 |
| 64 并发，仅一波同时到达 | 64/64 | 4.33 秒 | 14.79 次/秒 | 2.363 秒 | 4.169 秒 | 4.291 秒 |

固定到达速率阶段的客户端最多允许 8 个执行线程，实际观测到最多 3 个请求同时在途。
32/64 并发用线程屏障同时发起，吞吐是整波完成速度，不代表持续施压能力。

## 资源与排队分析

Qdrant 的 Docker 内存观测约为 **2.034—2.081 GiB**，API 为 **15.84—43.91 MiB**。
Docker 的内存统计与操作系统页缓存、进程 RSS 不是同一种口径，不能据此精确预测迁移后的
可用内存。这里也没有包括 rn 上既有服务的内存。

Qdrant CPU 采样大部分低于单核 70%，出现一次 **456.29%** 的短时读数；
Docker 的 100% 代表约一个 CPU 核心，并非全部 8 核。API 最高为 **11.09%**。
采样间隔约 3 秒，CPU 尖峰不能代表持续资源需求，也没有进一步归因这一次尖峰。

持续并发从 4 提高到 16，吞吐仅提高约 34%，中位延迟由 0.192 秒升至 0.867 秒。
结合代码中只有 4 个 embedding 槽位，可以判断继续堆积在途请求主要会增加排队；
当前记录没有分阶段 tracing，不能准确拆分模型网络、供应商计算与本地检索各自占时。

64 并发这一波的 P95 为 4.169 秒。在当前代码中，embedding 的 5 秒超时从等待槽位之前
开始计算。模型或网络稍慢就可能触发超时，所以不宜把 64 并发作为初始常态运行目标。

## 边界

- 本次没有修改生产代码、现有容器配置、模型并发限制或检索参数。
- 本地 API 和 Qdrant 在各阶段前后健康检查均成功，没有出现 HTTP 错误或客户端超时。
- 没有持续数小时、跨晚高峰测试，也没有覆盖真实用户查询长度和数据集过滤的全部分布。
- API 会把多种上游错误隐藏成通用 503；本次未出现 503，不代表供应商没有长期额度约束。
- 本次“并发”指同时在途的搜索请求；不等于每秒请求数，也不等于注册用户或在线用户数。
- rn 的容量须结合独立受限资源实验和其自身资源情况判断；不能按 CPU 核数等比例换算。
