# RN 亚洲及全球直连 / Cloudflare 代理实测

测试时间：2026-09-22 12:29:31–12:34:25，北京时间。
测试域名：`rn-proxy-test.anyveo.com`，源站 RN：`192.129.135.19`。

## 结论

**Cloudflare 橙云改善了两条不稳定线路，但本次没有普遍加速动态回源请求，
也不能据此宣称解决了亚洲丢包。当前域名的 Bot Fight Mode 还会拦截部分 API 客户端。**

- 北京移动与曼谷 Siamdata 两个节点，直连 HTTPS 均为 0/3，代理均为 3/3。
- 两种方式连续三轮都成功的 24 个节点，逐节点比较中位数，全部是代理更慢。
  合并样本中位数从 574.5 ms 增至 967.5 ms，p95 从 1,334 ms 增至 2,350 ms。
- 东京 AWS、首尔 AWS、新加坡 OVH、伦敦 OVH 每轮都收到代理侧 HTTP 403。
  已用 Cloudflare 安全事件确认来源为 Bot Fight Mode，不是源站故障或网络丢包。
- RN 的全量中文诗词检索容量仍约为 1.63–2.22 QPS，建议默认 2 并发、最多 4 并发试运行。
  本次轻量网络端点不涉及向量查询，不能用它推算诗词服务容量。

因此，RN 可用于低流量试运行；“普通 Cloudflare 橙云 + 当前域名设置”
不能直接作为面向亚洲用户的低延迟 API 方案通过验收。
建议把 RN 作为低流量候选，生产选址继续比较面向目标运营商的亚洲线路，
同时解决 API 被挑战的问题；迁移腾讯云或升级 RN 后均需重新实测。

## 测试设计及覆盖

使用 Globalping 分布式节点，申请 31 个位置，实际匹配到 30 个。
缺少上海阿里云 AS37963；其余节点在 8 次测量中的城市、ASN、网络及坐标元数据一致。
覆盖 17 个国家/地区、六大洲，其中亚洲 24 个节点。

亚洲包括中国大陆、中国香港、中国台湾、日本、韩国、新加坡、印度、泰国、
越南、印尼、马来西亚、菲律宾；其他包括美国、英国、澳大利亚、巴西、南非。
详细城市、ASN 和全部结果见 [30 节点表](proxy-node-table.md)。
这覆盖了多个主要云机房和运营商样本，不代表每个国家的全部机房或居民宽带。

| 项目 | 实际方法 |
| --- | --- |
| HTTPS | 三轮，每轮 30 个节点分别进行一次直连和一次代理请求；共 180 次 |
| TCP | 每节点每种方式各 16 次 TCP 443 连接，共 960 次 |
| 直连 | 目标 IP 为 RN，Host 与 TLS SNI 均为测试域名 |
| 代理 | 同一域名经 Cloudflare 公共 DNS 解析，橙云开启 |
| 响应 | `/rn-proxy-check` 返回轻量 JSON、源站标记、当轮 nonce 和实时戳 |
| 缓存 | `Cache-Control: no-store, max-age=0`；检查代理缓存状态及源站访问日志 |
| TLS | 有效 Let's Encrypt 证书；检查探针 `tls.authorized`；区域保持 Full (strict) |
| 时间限制 | HTTPS 每次 15 秒；TCP 测量 21 秒 |
| 时间配对 | 首轮两组提交相差约 32 秒；第二、三轮两组接近同时提交 |

HTTPS 测的是独立新连接，包含 TCP、TLS、响应传输；代理方式还包含 DNS。
没有在同一长连接上循环请求。生产客户端的连接复用可能改变结果，需要另测。
直连目标 IP 不产生域名查询，因此另行给出扣除 DNS 的比较。

162 个 HTTP 200 全部通过证书、nonce、源站响应体及响应头、禁用缓存校验。
代理成功的 78 次均为 `CF-Cache-Status: DYNAMIC`，没有 HIT。
源站日志按每轮 nonce 核对：直连每轮 28 条 200，代理每轮 26 条 200，
与探针成功数完全对应，支持这些动态请求确实到达 RN。

## 可用性：连接改善与业务成功率分开看

| 指标 | 直连 RN | Cloudflare 代理 |
| --- | ---: | ---: |
| 校验合格的 HTTP 200 | 84/90，93.3% | 78/90，86.7% |
| 连接 / TLS 超时 | 6/90 | 0/90 |
| HTTP 403 | 0/90 | 12/90 |
| HTTP 200 内容或 TLS 校验失败 | 0 | 0 |
| TCP 443 成功连接 | 472/480，98.3% | 480/480，100% |

每轮均为直连 28/30 成功、代理 26/30 成功，失败节点没有轮换。
代理侧所有请求都收到 HTTP 响应，不等于业务全部成功；403 仍然无法返回查询结果。
同样，TCP 连接失败比例不是物理链路丢包率；代理 TCP 只测到边缘，不包含回源。

两条改善明显的线路：

| 节点 | 直连 HTTPS | 代理 HTTPS | 直连 TCP 失败 | 代理 TCP 失败 | 代理成功耗时 |
| --- | ---: | ---: | ---: | ---: | --- |
| 北京移动 AS9808 | 0/3 | 3/3 | 6/16 | 0/16 | 中位 3,770 ms；1,451–3,791 ms |
| 曼谷 Siamdata AS56309 | 0/3 | 3/3 | 2/16 | 0/16 | 中位 1,051 ms；957–1,058 ms |

它们分别接入 HKG、SIN 边缘。北京移动虽然恢复了本轮可达性，等待时间仍较长。
不能用各 3 次成功认定问题长期消失。

## 公平的延迟对照

只比较两侧三轮全部成功的共同节点，避免将代理新增可达节点或被拦截节点混入均值。
p95 使用 nearest-rank；成功耗时统计排除失败，失败数仍完整保留在上一节。

| 同一批成功节点 | 样本数 / 每侧 | 直连 p50 | 代理 p50 | 直连 p95 | 代理 p95 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 全球 24 节点，总耗时 | 72 | 574.5 ms | 967.5 ms | 1,334 ms | 2,350 ms |
| 全球 24 节点，扣除 DNS | 72 | 574.5 ms | 940 ms | 1,334 ms | 2,268 ms |
| 亚洲 19 节点，总耗时 | 57 | 589 ms | 1,031 ms | 1,381 ms | 2,428 ms |
| 亚洲 19 节点，扣除 DNS | 57 | 589 ms | 972 ms | 1,381 ms | 2,346 ms |

24/24 节点各自的三轮中位数都在代理侧更高；逐节点中位增量为 343.5 ms。
全球合并中位数相差 393 ms，约增加 68.4%；这是另一种统计口径，不与前者混用。

代理确实缩短了部分握手过程，但动态结果返回更慢。共同 24 节点的分阶段中位数为：

| 阶段 | 直连 | 代理 |
| --- | ---: | ---: |
| TCP | 179 ms | 51 ms |
| TLS | 190.5 ms | 64 ms |
| 首字节等待阶段 | 183 ms | 812.5 ms |

首字节阶段包含边缘、安全处理、回源和源站处理，不能直接称为 Cloudflare → RN 的 RTT。
各阶段中位数也不能相加还原总耗时中位数。
代理三轮 DNS 中位数依次为 65.5、5、3 ms；扣除 DNS 后，总耗时中位数仍为
954、929.5、963 ms，高于同期直连的 577、568.5、573.5 ms。
因此本轮差异不能只归因于首次 DNS 查询。

## 403 根因与 API 部署影响

Cloudflare 安全事件中，首轮四个被拦截请求都显示：
`action=managed_challenge`、`ruleId=bot_fight_mode`、`source=botFight`。
四个 CF-Ray 分别为 `a3ee927b8c24e38f`、`a3ee927be828aa69`、
`a3ee927b48271d1c`、`a3ee927b7e33438f`，时间为 04:30:04 UTC。
后两轮同样四个节点收到 403；源站没有对应的额外请求或 403 记录。

当前 `anyveo.com` 开启免费 Bot Fight Mode。
[Cloudflare 官方说明](https://developers.cloudflare.com/bots/get-started/bot-fight-mode/)
明确该功能作用于整个区域，不能通过 WAF 自定义规则或 Page Rules 按路径绕过。
现有业务域名需要的防护保持原状，本次没有关闭整域 Bot Fight Mode。

生产 API 需要另外确定可行配置，例如使用单独区域承载 API，或评估支持细粒度控制的
防机器人产品。仅新建同一区域的子域名不能隔离免费 Bot Fight Mode。
这些属于后续部署选择，本次未新增付费功能或改动其他站点防护。
本轮证明的是这些无人值守探针会被挑战；不能推断所有用户浏览器都会失败，
但非交互 API 客户端无法依赖人工完成挑战，必须纳入实际客户端验收。

## 解释边界及复核材料

本次每节点仅 3 次 HTTPS 和 16 次 TCP，属于约五分钟的短时快照。
不能据此承诺长期 SLA、运营商全天表现或 1,000 QPS，也没有测得物理网络丢包率。
健康响应很小且无业务计算；真实查询还要增加 embedding、向量检索、数据库和鉴权耗时。
不能直接相加两个不同时间窗口的 p95，得出真实用户查询的 p95。

仅用 Cloudflare DNS 灰云不会改变用户到 RN 的业务路由；本次改善来自开启橙云后的路径变化。
本轮没有配置 Argo、付费加速或中国大陆网络产品，不能外推这些产品的效果。
