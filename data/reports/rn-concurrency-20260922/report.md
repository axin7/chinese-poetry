# rn 实机并发测试与 Cloudflare 代理评估

日期：2026-09-22，北京时间。rn 实机查询测试约在 03:25–03:36 进行；
Cloudflare 对照在 12:29–12:34 完成。

## 结论

**rn 可以运行全量诗词检索，适合低流量试运行。当前建议默认 2 个同时请求，
允许最多 4 个同时请求；先按全站约 1 QPS 做保守限流，再根据线上观测调整。**

中文多主题完整接口实测约 1.63–2.22 QPS。4 并发时 p95 为 2.28 秒；
8 并发时吞吐几乎不变，p95 增至 4.83 秒。主要资源问题是内存不足带来的换页与磁盘等待。
这里的 2/4 是试运行建议，8 是已测过的短批次，并非已经测得绝对最大并发数。

**Cloudflare 对照已完成：改善了两条不稳定线路，但没有普遍加速动态请求，
现有防机器人设置还拦截了四个节点。**
使用指定账号下的 `rn-proxy-test.anyveo.com`，30 个节点完成三轮 HTTPS 和一轮 TCP 对照。
直连成功 84/90，代理成功 78/90；代理另外 12 次为 Bot Fight Mode 的 403，连接超时为零。
共同成功的 24 节点，中位耗时从 574.5 ms 增至 967.5 ms，p95 从 1,334 增至 2,350 ms。
完整亚洲及全球结果见 [网络专项报告](network/report.md)。

## 1. 测了什么

| 项目 | 本次实际条件 |
|---|---|
| 服务器 | rn，2 vCPU，Xeon E5-2697 v2，约 2.41 GiB RAM |
| 原有服务 | 保留原有服务；测试结束后 OpenResty 仍显示 Up 7 weeks |
| 语料 | 已有译文的诗词，共 1,717,558 条句向量；未补译、未加入缺译内容 |
| 向量模型 | SiliconFlow `BAAI/bge-m3`，1,024 维 |
| 索引 | 全量 Qdrant，INT8 量化；与当前项目一致的 generation、top-1、ef=64 |
| 模型调用 | 当前实际配置 `EMBEDDING_CONCURRENCY=4`，超时 5 秒，关闭 rerank |
| Qdrant 测试预算 | 1.75 CPU、1,280 MiB RAM、RAM+swap 合计 2,304 MiB |
| API 测试预算 | 0.5 CPU、96 MiB RAM、不使用 swap |
| 测试入口 | rn 本机回环地址，不含用户公网、Cloudflare、会员鉴权或 Qwen 文案生成 |
| 完整请求 | 自然语言输入 → 远程 embedding → Qdrant → SQLite → 原文和译文 |

这些是保留现有服务时使用的隔离预算；没有升级服务器，也没有提高模型并发参数。
最初用 1,100 MiB RAM 启动 Qdrant，13 秒完成就绪，精确计数为 1,717,558，状态 green。
随后因宿主仍有物理内存余量、swap 接近用满，将测试容器 RAM 上限调整至 1,280 MiB，
再开始查询测试。不能把这些结果视为取消所有限制后的整机极限。

全量数据由干净停止的独立存储副本传输；91 个归档分片远端 SHA-256 全部通过，
SQLite 与 API 程序的哈希也与本地一致。索引位于宿主目录，独立于容器生命周期。

## 2. 中文真实使用方向的结果：主要容量依据

查询来自 144 类主题与两种有实际含义的偏好，共准备 288 条唯一中文输入。
固定随机顺序混合山水、亲情、爱情、历史、战争、哲理、劳作、节庆、艺术等主题。
实际发出 147 条不同输入，返回 127 部不同作品，147/147 均成功且原文、译文非空。
没有用重复输入制造应用层响应缓存命中；向量库与操作系统内部缓存仍然存在。

| 同时请求数 | 成功 / 总数 | 实际时长 | 成功 QPS | p50 | p95 | 最慢 |
|---:|---:|---:|---:|---:|---:|---:|
| 2 | 41/41 | 25.23 秒 | 1.63 | 1.15 秒 | 1.56 秒 | 2.28 秒 |
| 4 | 58/58 | 26.54 秒 | 2.19 | 1.89 秒 | 2.28 秒 | 2.32 秒 |
| 8 | 48/48 | 21.61 秒 | 2.22 | 3.51 秒 | 4.83 秒 | 4.93 秒 |

2、4 并发阶段各计划持续发请求 25 秒；表中耗时包含最后请求完成。
8 并发阶段设定最多 48 次请求，因此属于约 21.6 秒的封顶批次，不是长时间持续负载。
8 并发脚本因 p95 超过预设 4 秒阈值返回退出码 1；**HTTP 错误为零**，并非服务崩溃。

4 → 8 并发，吞吐只提高约 1.7%，p95 变为约 2.12 倍，收益很低。
如果希望源站响应大部分落在 2 秒内，2 并发更合适；能接受约 2–3 秒尾延迟时可用 4 并发。
用户侧还要叠加公网访问、鉴权与前端时间，不能把表中源站时延直接当作用户总等待时间。

## 3. 为什么不能用最高测得的 9.7 QPS 作为通用容量

同一台 rn 上，还测了唯一英文模板输入，每档约 25 秒：

| 同时请求数 | 成功请求 | QPS | p95 |
|---:|---:|---:|---:|
| 1 | 30 | 1.18 | 1.14 秒 |
| 2 | 74 | 2.91 | 0.99 秒 |
| 4 | 149 | 5.88 | 1.00 秒 |
| 8 | 250 | 9.69 | 1.14 秒 |
| 16 | 251 | 9.46 | 2.05 秒 |

英文 754/754 成功，返回 249 部不同作品。它证明这组输入在短时测试中可以处理 16 并发，
但主题与语言分布、相近查询的索引访问局部性、预热状态均不同于中文广泛主题。
9.7 QPS 不应作为所有自然语言输入的承诺。

另外直接轮转查询 128 个已有向量，省去模型和 SQLite 后，rn 实测如下：

| 向量并发 | 成功 / 总数 | QPS | p95 |
|---:|---:|---:|---:|
| 1 | 48/48 | 1.90 | 0.89 秒 |
| 2 | 84/84 | 3.29 | 1.33 秒 |
| 4 | 58/58 | 2.23 | 3.02 秒 |
| 8 | 102/102 | 3.72 | 4.92 秒 |

这 292 次查询全部成功。各阶段吞吐不单调，说明短样本与工作集差异很大。
英文完整接口更快不表示增加 embedding 能提升向量性能；不同输入不能直接相减来估算组件耗时。

本地 M2 的完整接口曾达到持续 16 并发、约 16.5 QPS；本地受限向量实例达到 38–66 QPS。
这些是另一台机器及不同交换区的结果，不能作为 rn 容量。详见对应原始报告。

## 4. 资源瓶颈：主要是内存与磁盘等待

中文查询期间，主机与容器采样如下：

| 指标 | 中文 2 并发 | 中文 4 并发 | 中文 8 并发 |
|---|---:|---:|---:|
| Qdrant RAM 最高 | 约 1,280 MiB | 1,280 MiB | 约 1,280 MiB |
| Qdrant swap 最高 | 813.65 MiB | 789.86 MiB | 815.38 MiB |
| 主机 CPU iowait | 41.16% | 52.10% | 54.23% |
| 主机可用 RAM 最低 | 309.60 MiB | 306.79 MiB | 329.89 MiB |
| 主机空闲 swap 最低 | 76.71 MiB | 101.64 MiB | 30.62 MiB |

向量查询窗口约 104 秒内，主机换入约 1,927 MiB、换出约 1,619 MiB，
Qdrant major fault 增加约 49 万次。向量与英文完整接口窗口内，Qdrant CPU 配额节流增量均为 0，
未发生 OOM。英文阶段 API 内存峰值约 40.79 MiB。

这说明索引确实在借用磁盘交换空间，且查询经常等待内存页从磁盘读回。
主机指标包含其他进程，但 Qdrant 自身的缺页、读写及内存限制事件提供了相互印证。
并非只看到了“配置了 swap”，也没有把解压归档时的磁盘活动混入上述查询窗口。

如果继续保留现有服务，优先考虑至少 4 GiB RAM，8 GiB 可给页缓存与维护留下更多余量；
升级后仍需重新压测，不能预先承诺具体 QPS。单纯增加允许并发数不能消除当前瓶颈。

rn 到 SiliconFlow 的独立小批次也已验证：36/36 个中文 embedding 请求成功，
1/2/4 并发批次吞吐为 1.83/3.05/5.35 次/秒，p95 约 0.95–1.16 秒。
这包含新 HTTPS 连接且当时仍在传输索引，不等于完整接口或供应商长期配额上限。

## 5. Cloudflare 能否解决丢包

**实测改善了部分线路的可达性，但当前配置不能视为亚洲低延迟 API 的完整解决方案。**

在用户指定账号下创建 `rn-proxy-test.anyveo.com`，签发有效证书并保持 Full (strict)。
使用禁止缓存的动态 JSON 健康入口，三轮 HTTPS 均为同一批 30 个节点，
覆盖 17 个国家/地区、六大洲，含 24 个亚洲节点。另做每节点每侧 16 次 TCP 连接测试。
31 个计划位置实际匹配到 30 个，缺少上海阿里云 AS37963。

| 指标 | 直连 | Cloudflare 代理 |
|---|---:|---:|
| HTTP 200 且全部校验通过 | 84/90 | 78/90 |
| 连接 / TLS 超时 | 6 | 0 |
| HTTP 403 | 0 | 12 |
| TCP 连接成功 | 472/480 | 480/480 |
| 共同成功 24 节点 p50 | 574.5 ms | 967.5 ms |
| 共同成功 24 节点 p95 | 1,334 ms | 2,350 ms |

北京移动 AS9808 和曼谷 Siamdata AS56309，直连各 0/3 成功，代理均 3/3 成功。
直连 TCP 分别失败 6/16、2/16；代理均为 0/16。连接失败比例不能等同物理丢包率。
共同成功节点的三轮中位数全部在代理侧更慢；扣除 DNS 后代理合并 p50 仍为 940 ms。
多个中国大陆节点经 AMS（阿姆斯特丹）接入，没有保证就近进入亚洲机房。

东京 AWS、首尔 AWS、新加坡 OVH、伦敦 OVH 连续三轮收到 403。
Cloudflare 安全事件确认 Bot Fight Mode 发起挑战，源站无对应额外请求。
免费 Bot Fight Mode 不能按子域名或路径通过 WAF 规则豁免，本次保留整域现有防护。
这需要生产 API 单独解决，不能把收到 403 统计为成功，也不能把它称为网络丢包。

全部 162 个成功响应均通过 TLS、源站标记、nonce、no-store 校验；
78 个代理成功响应均为 DYNAMIC，源站日志条数与各轮成功数完全一致。
这些是约五分钟的短样本；轻量健康入口的网络结果不能替代上面的诗词查询容量测试。
仅使用 DNS 灰云不改变业务路由，橙云也不会修复源站内存与磁盘等待。
全部节点、方法、限制和原始数据见 [网络专项报告](network/report.md)。

先前误选的 `dsjworkforce.com` 下未创建过测试 DNS、站点或证书，已核对无本次配置可删。
早前 50 节点直连测试涉及不同时间及旧入口的过期证书、502，保留为历史基线，
不与本次有效证书、动态 200 的测量混合统计。

## 6. 建议与收尾状态

- 早期试运行：默认 2 个同时请求，入口先限流约 1 QPS；可接受较长响应时放宽到 4 并发。
- 约 2 QPS 是本次广泛中文样本的观测水平，不是已证明可全天维持的 SLA。
- 8 并发已观察到接近 5 秒的尾延迟，当前不建议把它设为常态目标。
- 这些并发数不是在线用户数；在线人数还取决于每人多长时间查询一次。
- 后续生产验收还需要固定到达速率、长时间运行、真实输入分布及网络高峰时段测试。

完整接口总计 901/901 成功；6 部不同作品的全文接口也通过原文/译文数组对齐检查。
两个专用测试容器已停止。Qdrant 退出 143 对应本次主动发送的 SIGTERM，OOM=false；
API 退出 0。原有 OpenResty 保持运行，new-api 仍保持原先的退出状态。

用户随后确认 rn 没有正在使用的服务，并授权清理磁盘。已删除远端传输压缩分片、
五个传输样本和旧归档 journal；本地完整备份与校验记录保留。
两阶段清理完成，根分区可用空间从 **2.88 GiB 增至 19.94 GiB**，共释放 **17.06 GiB**，
磁盘使用率从 **93% 降至 52%**。额外清理了已停止容器的旧日志、13 份历史应用日志
及两份旧升级下载目录，完整删除清单见 [清理记录](network/cleanup-report.md)。
完整向量存储、SQLite、应用配置和回滚备份保留；删除的旧日志未备份，无法通过本次任务恢复。
释放磁盘空间不等于增加物理内存，上面的查询容量结论尚未因清理而重新测量。
安装测试证书环境等后，12:35:44 复查可用空间为 19.683 GiB，使用率仍为 52%。

测试 DNS 与轻量 HTTPS 入口保留；根路径返回 404，公网未开放诗词业务接口。
证书于 2026-12-21 03:27:45 UTC 到期，临时站点未配置自动续期，
持续保留时需按 [源站说明](network/origin/origin-notes.md) 续期。
这不是已配置公网诗词入口和自动恢复策略的生产部署。
