# 测试口径与证据边界

本附录说明本地、资源限制与远程模型探测的口径。
rn 全量实机测试现已完成，中文与英文结果见[最终报告](../report.md)。
Cloudflare 同源成对 HTTP 对照尚待完成；短时实机测试也不能作为长期容量承诺。

## 并发、吞吐与在线人数

- 在途并发：同一时刻已发出但尚未收到完整响应的请求数。
- QPS：单位时间完成的请求数；报告使用成功数除以阶段实际耗时，包含末尾排空。
- 在线人数：正在使用产品的人数；需知道每人的请求频率才能换算为请求负载。
- 稳定负载下，平均在途数约等于成功吞吐乘以平均响应时间；错误与排队需另计。

因此，“16 个请求同时在途”“每秒 16 个请求”和“16 个在线用户”不是同一个指标。
闭环压测中，每个客户端完成一次请求才发下一次；延迟升高会自动降低到达速率。
它不能证明固定速率持续涌入、排队不断增长时仍然稳定。

## 当前配置与测试链路

应用源码的 `EMBEDDING_CONCURRENCY` 默认值为 16，**现有本地运行配置实际为 4**。
本次 rn API 同样显式沿用 4，没有把源码默认 16 的结果当成当前配置。
embedding 的 5 秒超时从等待并发槽位之前开始计时，排队会消耗同一预算。
应用检索并发上限 256、HTTP 在途上限 512 是保护阈值，不是已验证容量。

| 已完成测试 | 实际经过的链路 | 没有覆盖的部分 |
|---|---|---|
| 本地全链路，1,232 次不同文本 | HTTP API、SiliconFlow embedding、全量 Qdrant、SQLite 取文 | rn 硬件、用户公网入口、Cloudflare、应用外部鉴权 |
| 本地资源限制，5,685 次向量查询 | HTTP、Qdrant 全量索引 | embedding、SQLite、业务 API、公网入口 |
| rn 模型探测，36 次中文请求 | rn 到 SiliconFlow HTTPS、embedding、维度校验 | Qdrant、SQLite、业务 API、用户到 rn 的网络 |

本地全链路使用从未重复的合成英文查询，避开按精确文本匹配的向量/响应缓存。
每次验证 HTTP 200、原文及译文非空；另抽查 3 部作品的全文数组对齐。
这验证内容结构，不等于逐条验证检索相关性；也不是现实用户查询分布的完整样本。

资源限制试验轮转使用 **128 个已存储向量**，在约 25 秒的每档测试中反复检索。
这些向量无需模型计算，且重复的小工作集可能受益于 CPU、内存及页缓存。
“每次都调用 Qdrant”不能消除这些局部性收益，也不能代表不断变化的自然语言检索。

## 本地硬件与 rn 的差别

本地是 Apple M2、24 GiB 宿主内存，Docker 虚拟机有 8 个 CPU、约 11.74 GiB 内存。
rn 先前盘点为 2 vCPU、Xeon E5-2697 v2、总内存约 2.41 GiB，并运行既有服务。
CPU 架构、单核速度、磁盘、虚拟化和内存竞争均不同，不能按核心数直接换算 QPS。

本地隔离容器限制为 2 CPU、1,280 MiB 物理内存；允许额外 1,024 MiB swap 后可以启动，
禁用 swap 时冷启动 OOM。允许 swap 的检索出现大量换页，历史 swap 峰值 933.3 MiB。
本地虚拟机使用 zram 及磁盘交换区，bind mount 被标记为 FUSE；rn 的交换区、磁盘及
可用内存不同。实验只证明这一受限环境可以工作，不能证明 rn 有相同吞吐或尾延迟。

## 样本时长与延迟

本地全链路 4、16 并发分别持续约 25 秒发请求，实际完成吞吐为 12.31、16.52 次/秒。
64 并发仅发送一波，64 次全成功，P95 为 4.169 秒；不是 64 并发持续施压测试。
最初每档 60 请求的摸底有些仅持续约 3 秒，不能替代后续较长阶段。
这些测试均未覆盖数小时运行、亚洲晚高峰、供应商长期配额或用户分布变化。

rn 模型探测每档只有 12 次；1、2、4 并发的批次吞吐为 1.83、3.05、5.35 次/秒。
全部返回有效 1,024 维向量，但含首次 HTTPS 建连，且同期正在传输完整索引。
5 秒为 Python 网络操作超时，不是 Go 应用包含排队的 5 秒总预算，不能混用口径。
小样本 P95 使用插值计算，仅描述当前样本；未测到失败不等于证明长期无失败。

## Cloudflare 测试应如何解读

DNS 仅解析地址时不会改变业务数据路径；开启代理后，用户先连接 Cloudflare 边缘，
未缓存请求仍须由边缘回源 rn。边缘 TCP 建连快，只证明第一段连接快。
ICMP 可能被限速或过滤，边缘 ping 的低延迟、低丢包也不能证明完整 HTTPS 请求改善。

有效对照须使用同一源站、等价请求与负载、相近时间、同一批地区/运营商，分别访问
直连和代理入口，核对 TLS、HTTP 状态、响应内容、总耗时和失败率。
应确认缓存确实未命中，并保留每轮原始结果；缓存命中或 Cloudflare 错误页不能算回源成功。
代理可能改变路由并改善某些线路，也可能增加绕路；结果须按地区、运营商分别判断。
即使入口网络改善，也不会自动提高 rn 的内存容量、磁盘性能或模型供应商配额。
