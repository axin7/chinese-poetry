rn 部署容量与全球网络评估
测试日期：2026-09-22，北京时间。目标：rn（192.129.135.19）。

**结论**

不建议将当前全量诗词服务部署在这台 rn 上作为面向亚洲用户的生产主节点。
现有内存与部署恢复空间不足；针对每秒 1,000 次、基本无缓存命中的自然语言检索，
当前机器与在线 embedding 并发不足，供应商配额是否满足目标尚未验证。

网络表现具有明显地域及运营商差异。日本、韩国云机房和香港的样本相对较好；
北京移动出现可复现的 TCP 建连失败与 HTTPS 超时；
部分东南亚线路延迟高、存在长尾。现有证据不能推导为该服务商所有机器或亚洲所有线路都差。

轻量代理或辅助服务可以单独评估，当前 rn 不适合承担完整向量检索主库。
本次没有把诗词服务部署到 rn，也没有执行服务启停、证书续期或防火墙配置修改。

**测试范围与方法**

硬件与出站检查约在 01:05–01:15；全球主要探测窗口为 01:09:06–01:12:36。
这是凌晨短时抽测，没有覆盖亚洲晚高峰，也不是长期可用性承诺。

- 全球主样本：50 个探针，21 个国家和地区，覆盖亚洲、欧洲、北美、南美、非洲、大洋洲。
- 亚洲占 38 个探针；主样本中 45 个为机房网络、5 个为用户接入网络。
- 机房包含腾讯云、阿里云、AWS、Google Cloud、Oracle、华为云、OVH、Akamai、xTom 等。
- ICMP：同一批 50 个探针，两轮、每轮 16 次，共 1,600 次。
- TCP 443：主样本每点 16 次；另对 37 个亚洲城市/ASN 组合复测，共 1,392 次建连探测。
- HTTPS：主样本每点一次 HEAD，另有一次东京校准测试。
- TCP MTR：11 个亚洲城市/ASN 组合及一个圣保罗对照；每跳请求上限 16 次。
- 服务器本地：资源、进程、容器、监听、防火墙、时钟、IPv6、外部依赖连通性、
  短时顺序读，以及往返 Cloudflare 测速端点各三次 10 MiB 数据传输。

首轮 TCP、HTTPS 和两轮 ICMP 使用同一批探针。
第二轮 TCP 只保证同城市与 ASN，18/37 项探针元数据发生变化；MTR 同样不能保证同一物理探针。
不能将这些探测解释为全部亚洲居民、全部机房或所有时段的用户体验。

直接以源站 IP 为目标，HTTPS 指定 Host 为 code.fengxin.me，
没有把 Cloudflare 边缘节点的响应误算成源站性能。
该方法也没有验证将来的诗词域名、Worker 回源、Tunnel、DNS 切换或会员鉴权。

以及面板与代理服务。即使清理非必要服务，也不能据此承诺全量高并发检索。
本次没有清理或关闭它们。

**路由诊断能说明什么**

东京 AWS 的路径经过东京与洛杉矶的 Cogent 节点，终点约 105 ms。
新加坡 xTom 的路径经过 Global Secure Layer 的新加坡/洛杉矶节点及 Cogent。
台湾样本出现东京、美国西海岸多个骨干节点；泰国、马来西亚样本可见
新加坡、东京、洛杉矶的 Arelion/Twelve99 节点。说明不同上游与跨洋路由会带来明显差异。

MTR 在上海阿里云、广州电信、金奈和吉隆坡报告了较高终点探测丢失，
但与普通 TCP 成功率不一致。它们采用不同探针主机或探测方式，
不能据此认定相同百分比的业务请求丢失，也无法单独定位故障责任方。

韩国 KT 和泰国 Siamdata 两份 MTR 明确标记为探针内部失败，
不计作 rn 服务中断。吉隆坡 MTR 终点只完成了 11 个样本。
中间跳不回复或高丢包更不能直接判定转发链路丢包。

**HTTPS 入口与现有服务**

50 个主 HTTPS 样本中，49 个能够收到源站 HTTP 响应，但全部返回 502；
另一个是上述北京移动的 TCP 建连超时。
49 个响应均报告证书过期，证书到期时间为 2026-06-06 14:25:37 UTC。
严格校验的 curl 也以错误 60 失败。

因此这些 HTTPS 时延只是“握手并收到 502 响应头”的时间，不是业务成功响应时间。
测试工具为诊断继续处理了无效证书；正常客户端不能据此视为可用。

源站旧服务 new-api 的本地 3000 端口拒绝连接。
容器状态为 exit 2、OOM=false，结束于北京时间 01:06:53；
分布式 HTTPS 探测开始于 01:09 之后。退出根因未在本次容量评估中确定。
这解释了当前旧站点不能作为健康业务验收端点，但不等于将来的诗词服务必然返回 502。

服务器 80/443 已监听且防火墙放行，部署基础存在。
另有约 12,018 条逐 IP REJECT 规则，后续高新建连接率场景值得单独压测；
本次没有证明这些规则导致北京移动异常。

新诗词域名需要有效证书、正确上游和 Worker 到源站的鉴权。
Qdrant 6333/6334 应继续保持私网/回环访问。
当前本地 compose 的 API 仅绑定回环地址，不能直接当作已经配置好的公网部署。

401 在这里只说明 DNS、TCP、TLS 和应用入口可达。
本次未用凭证调用模型，没有测得模型推理耗时、有效账户配额、TPM 或实际 embedding 吞吐。
当前 Go 客户端会复用连接，上表每次新连接的总耗时也不是每次生产调用固定要支付的成本。
.cn 与 .com 的账户、配额和模型可用性需要分别确认，不能仅因网络更快直接替换。

到 Cloudflare 测速端点三次 10 MiB 下载为约 277–293 Mbps，
三次上传为约 177–250 Mbps。这是近端短时吞吐，不是亚洲公网带宽或带宽保证。
没有核验商家月流量包、突发限速和晚高峰拥塞。

按每次响应 2–5 KB 粗算，1,000 QPS 仅响应体约需 16–40 Mbps；
若全天持续，约为 173–432 GB/天、5.2–13 TB/30 天。
这只是满载预算，不是预测实际消费。1024 维 float32 embedding 原始数据另有约
32.8 Mbps 的入站传输下限，JSON 及协议开销还会增加流量。

rn 的近端基础吞吐不是本次最明显的短板；内存、空间、跨洋延迟及模型服务能力更关键。

**每秒 1,000 次语义检索的约束**

当前 API 的未缓存文本请求需要在线调用 SiliconFlow 生成查询向量，
再到 Qdrant 检索并查询 SQLite。现有预计算诗词向量不能省去这一查询 embedding 步骤。

- 当前实际本地 API 配置 EMBEDDING_CONCURRENCY=4，源码默认值为 16。
- 该并发值与离线导入共用配置；原样部署会继承 4，而不是自动变成 1,000。
- 每次未命中文本查询单独调用一次模型，当前没有跨请求在线合批。
- 1,000 次唯一查询/秒意味着至少 60,000 embedding RPM，以及相应 TPM。
- 假设一次 embedding 平均用时 500 ms，需要约 500 个并行请求才能维持 1,000 QPS，
  还没有计入余量；这是容量算术，不是实测延迟。
- 现有搜索并发默认 256、HTTP 在途上限 512，查询 timeout 10 秒，
  embedding timeout 5 秒，等待 embedding 槽位也会消耗它的超时。
- 提高这些数值不能补足供应商配额、CPU、内存或网络能力。
- 本次没有将全量语料恢复到 rn，也没有对 rn 进行 1,000 QPS 业务压测。
  不能把 ping、近端测速或当前错误响应延迟写成语义检索吞吐。

**部署建议与验收条件**

| 使用目标 | 对当前 rn 的判断 | 建议 |
|---|---|---|
| 全量数据、低频开发验证 | 不建议原样部署，内存和恢复空间过紧 | 参考 4 核/8 GiB，至少 40–50 GiB 可用 SSD 空间 |
| 面向亚洲的正式诗词主服务 | 不推荐作为唯一源站 | 优先测试香港、日本、新加坡等靠近目标用户和模型服务的候选线路 |
| 1,000 QPS、无缓存语义搜索 | 当前不满足 | 可从 16 个独享 vCPU/32 GiB/100 GiB NVMe 开始性能验证，不能保证即达标 |
| 辅助反代或轻量非核心服务 | 可另行考虑 | 先解决对应域名证书、上游健康与访问控制 |

内存估算并不要求本机部署大语言模型；当前方案仍是远程 embedding/平台模型调用。
离线导入、索引构建留在其他机器完成，只迁移已完成的数据与匹配的 SQLite generation。
不要为了迁就 rn 而直接更改维度或索引模型，这会涉及重建和检索质量验证。

Cloudflare Worker 可以承担会员校验、配额和统一入口，但回源仍要到 rn。
它不会自动补足 rn 的内存，也不能保证消除跨洋延迟和不稳定路由。
本次未部署 Worker/Tunnel，因此没有将“rn 到 Cloudflare 很快”解释为亚洲用户全链路很快。

新机器的验收应分两层：
先用预计算的多样查询向量测 Qdrant+SQLite，再测无缓存文本端到端链路；
按 100/300/500/1,000 QPS 逐级恒定到达率压测，记录错误率、p95/p99、429、
内存、CPU、磁盘延迟和检索质量，同时验证模型供应商的 RPM/TPM。
业务延迟及错误率阈值应由产品目标确定，不能由本次短探测替代。

亚洲线路需要在当地晚高峰再次抽测，尤其是北京移动及已有秒级尖峰的线路。
现有 16/32 个样本即便零失败，也不能证明长期丢包低于 1%；
本次结果足以识别已出现的问题，不足以认证低故障率 SLA。
